# Live-Switch Benchmark Incident Resolution — v1.21 Checkpoint

**Date:** August 21, 2026
**Project:** `cpython-extensions` / `python_extensions.switch`
**Component:** CPython 3.13 live self-modifying switch backend
**Status:** Corrective benchmark implemented; multi-site live compiler defect found and fixed

## What changed

The original incident correctly identified a benchmark-design problem: comparing one-call-per-dispatch direct-value switches overstates the portable backend and does not exercise the live backend's intended repeated in-frame dispatch workload.

The corrective implementation now benchmarks the **real** `@enable_switch(mode="fast")` generated bytecode against the **real** `@enable_switch(mode="portable")` balanced backend from identical source. It performs many internal switch dispatches per outer Python call, validates semantics before timing, checks compiler telemetry, alternates timing order, and aggregates isolated-process medians.

During that work, a separate implementation defect was discovered.

## Implementation defect discovered

A generated hot loop with four 64-route switch sites failed during `mode="fast"` compilation with:

```text
python_extensions.switch.SwitchError:
failed to locate inline switch gate or constant markers
```

### Root cause

`_locate()` assumed the synthetic gate scaffold compiled as four adjacent semantic instructions:

```text
LOAD_CONST gate_a
STORE_FAST temp_a
LOAD_CONST gate_b
STORE_FAST temp_b
```

Once a large generated function exceeded the one-byte constant-index range, CPython 3.13 inserted `EXTENDED_ARG` before later `LOAD_CONST` instructions. The locator no longer recognized the gate. More importantly, a live patch starting at the `LOAD_CONST` rather than its `EXTENDED_ARG` prefix would leave a stale prefix immediately before the replacement `JUMP_FORWARD`, corrupting the jump argument.

### Fix

The live locator now:

- treats `EXTENDED_ARG` and inline `CACHE` entries as transparent while recognizing the synthetic gate pattern;
- walks backward to the first `EXTENDED_ARG` prefix belonging to the initial gate instruction;
- binds the writable live gate at that prefix, so the replacement jump overwrites the complete prefixed instruction start;
- accepts `EXTENDED_ARG` prefixes before synthetic `STORE_FAST` marker targets as well;
- retains the original 1/2/4-code-unit encoded jump widths and forward-target validation.

The reserved assignment scaffold remains at least four code units wide; large operands may make it wider, which is safe because execution transfers away through the patched jump.

## Regression coverage

New regressions cover:

1. identical-source portable-balanced vs real live-inline hot loops;
2. four 64-route switch sites, which pushes later synthetic constants beyond index 255;
3. functions with more than 255 local variables, forcing `EXTENDED_ARG` on local operands;
4. backend telemetry and live-gate counts;
5. portable/fast semantic equivalence including misses.

Qualification after the fix:

```text
Full pytest suite:                 440 / 440 passed
Live compatibility stress:         1,239,100 calls passed
```

## Real-backend performance evidence

All numbers below are medians of isolated-process medians and represent the actual generated backends, not a `ctypes` proxy.

### Dispatch-dominant workload, one switch site, random traffic

| Routes | Portable balanced | Live fast | Portable / fast |
|---:|---:|---:|---:|
| 16 | 86.15 ns | 85.64 ns | 1.01× |
| 64 | 105.41 ns | 79.11 ns | 1.33× |
| 256 | 127.86 ns | 93.23 ns | 1.37× |
| 1,024 | 206.41 ns | 100.36 ns | 2.06× |
| 2,048 | 246.57 ns | 105.43 ns | 2.34× |

The crossover is workload-dependent. Small general switches can be close; the live backend becomes increasingly attractive as balanced route-selection depth grows.

### 1,024 routes, one switch site, traffic sensitivity

| Traffic | Portable balanced | Live fast | Portable / fast |
|---|---:|---:|---:|
| Alternating | 178.39 ns | 81.02 ns | 2.20× |
| Random | 206.41 ns | 100.36 ns | 2.06× |
| Sequential | 173.99 ns | 86.25 ns | 2.02× |
| 90/10 skewed | 164.52 ns | 79.31 ns | 2.07× |

The advantage is therefore not limited to one favorable selector pattern.

### 64 routes, random traffic, increasing static switch sites

| Sites per loop iteration | Portable balanced | Live fast | Portable / fast |
|---:|---:|---:|---:|
| 1 | 105.41 ns | 79.11 ns | 1.33× |
| 4 | 104.41 ns | 88.38 ns | 1.18× |
| 8 | 104.68 ns | 90.94 ns | 1.15× |
| 16 | 108.59 ns | 94.54 ns | 1.15× |

The repaired live compiler now handles the 1/4/8/16-site dimension that originally exposed the locator defect.

### Heterogeneous whole-workload body, random traffic

| Routes | Portable balanced | Live fast | Portable / fast |
|---:|---:|---:|---:|
| 64 | 195.17 ns | 147.85 ns | 1.32× |
| 256 | 223.05 ns | 160.62 ns | 1.39× |
| 1,024 | 285.19 ns | 174.02 ns | 1.64× |

These rows include heterogeneous arithmetic and nested control flow rather than a minimal dispatch-dominant body.

## Scope and interpretation

This corrective work does **not** establish that live mode is universally faster.

Direct-value portable switches remain a separate specialization. When the complete result can be represented by a bound `dict.get`, portable mode is close to a minimum-cost Python implementation and can beat a live gate write.

The corrected conclusion is:

- **direct-value/simple lookup workloads:** portable direct-value specialization is generally preferred;
- **small general control-flow switches:** benchmark the real workload; either backend may win;
- **large general/heterogeneous switches in hot loops:** the real live backend shows a substantial and increasingly clear advantage in this environment;
- **multi-site hot loops:** supported after the `EXTENDED_ARG` locator fix, with explicit regression coverage.
