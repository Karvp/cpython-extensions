# Live switch architecture and performance

This document describes the explicit CPython 3.13 self-modifying switch backend introduced before 1.2.0 and substantially renovated for the 1.2.0 release line.

Live switch is an **opt-in execution architecture**. It is not the default implementation of `@enable_switch` and it should not be treated as a universal replacement for the portable compiler.

## 1. Execution model

Portable and live switch share source syntax and case semantics, but lower general control flow differently.

A general portable route is conceptually:

```text
subject
  -> dictionary lookup
  -> route id
  -> balanced inline route selection
  -> selected case body
```

A live route is conceptually:

```text
subject
  -> lookup encoded jump destination
  -> write live jump gate
  -> JUMP_FORWARD
  -> selected inline case body
```

The important workload distinction is **in-frame repetition**. Live mode is designed for one outer Python invocation that repeatedly dispatches among many heterogeneous inline code regions, as in a VM, parser, emulator, or hot state machine. Calling a switch function once per operation removes much of that advantage.

## 2. Public modes

`enable_switch()` accepts these execution modes:

| Mode | Mutation model | Concurrency/re-entry contract |
|---|---|---|
| `auto` | portable only unless an explicit `live_threshold` opts into isolated live dispatch | portable contract by default |
| `portable` | no raw bytecode mutation | thread-safe/re-entry-safe |
| `isolated` | cached live clone per thread and active depth; generators/coroutines use fresh clones per call | bounded isolation |
| `per_call` | fresh live code clone every invocation | strongest isolation, highest setup cost |
| `thread_local` | one live clone per thread | not re-entry-safe within a thread |
| `fast` | one shared live code object | only for a proven single-active-call execution model |

`fast` is intentionally dangerous when used outside its contract: concurrent or re-entrant calls can race on the shared jump gate. Prefer `isolated` when the execution model is not strictly single-active-call.

## 3. Live engines

Live modes also accept:

```python
@enable_switch(mode="fast", live_engine="auto")
```

`live_engine` is one of:

- `auto` — run the runtime/layout self-tests; use the native fused dispatcher when available, otherwise use the ctypes engine;
- `native` — require `python_extensions._livegate`; fail explicitly if it is unavailable or fails self-test;
- `ctypes` — force the historical Python/ctypes gate mechanism for diagnostics and comparisons.

The engine choice does not change case semantics. It changes how lookup and jump-gate mutation are executed.

## 4. Native fused dispatcher

The native accelerator lives in `src/python_extensions/_livegate.c` and is a normal CPython 3.13 C extension. It is deliberately not built against the Limited API/abi3 because live dispatch depends on the exact CPython 3.13 runtime contract.

The historical live hot path performs a Python-visible route lookup and then a ctypes scalar store. The fused native path combines lookup and gate mutation into one bound C call. Its dispatcher can additionally select semantics-safe specialized routing structures:

- contiguous/dense exact-integer lane;
- sparse exact-integer open-addressing table;
- exact-builtin typed partitions that avoid constructing `(type(subject), subject)` when user code cannot be invoked by the shortcut;
- conservative Python-dictionary fallback whenever ordinary Python hash/equality behavior must remain authoritative.

The integer lanes are deliberately restricted. Ordinary Python case mode must preserve aliases such as `True == 1` and `1.0 == 1`; an exact-int shortcut is therefore enabled only when the plan proves that bypassing those alternate key types cannot change semantics. Typed mode can optimize its exact-int partition independently because exact runtime type is part of key identity.

Small integer extraction uses CPython 3.13's compact-integer API after an exact-`int` check. Huge integers fall back to overflow-aware conversion/dictionary handling rather than being treated as misses.

## 5. Runtime self-tests and fail-closed behavior

Before a live engine mutates generated bytecode, `switch.py` validates the CPython code-object layout and a reversible probe write. The native engine has a separate write/self-test for every supported gate width.

If the assumptions do not hold:

- `live_engine="native"` raises `UnsupportedRuntimeError`;
- `live_engine="auto"` can fall back to ctypes when only the native accelerator is unavailable;
- portable mode remains unaffected.

The live compiler also handles `EXTENDED_ARG` prefixes when locating and binding generated jump gates. This matters for large or multi-site generated functions whose constant/local indexes exceed one-byte operands. Regression tests intentionally force both >255 constant and >255 local indexes.

## 6. Free-threaded CPython

Live self-modifying execution is **not certified for free-threaded CPython 3.13**.

`switch.py` checks `sysconfig.get_config_var("Py_GIL_DISABLED")` before importing the native extension. On a free-threaded build it does not import `_livegate`, because importing a C extension that does not declare no-GIL support can change interpreter-wide GIL behavior. Live modes are rejected; portable switch remains available.

Do not import `python_extensions._livegate` directly on a free-threaded build and infer support from successful import.

## 7. Workload selection

### Strong candidates

Use live mode as a serious optimization candidate for:

- bytecode VMs and interpreters;
- emulator/opcode loops;
- dense integer token/parser dispatch;
- large heterogeneous integer state machines;
- other functions that perform many switch operations inside one outer invocation.

### Benchmark first

Benchmark before choosing live for:

- mixed event buses;
- typed heterogeneous routing;
- moderate state machines;
- sparse integer protocols whose portable plan can use a compact statement template.

### Prefer portable

Portable is normally preferable for:

- HTTP/path routers;
- RPC method selection;
- one router function call per request;
- short async handlers;
- direct-value routes that reduce to approximately a dictionary lookup;
- expression/statement-template-compatible cases;
- heavy case bodies where dispatch is a small fraction of total work.

## 8. Extensive 1.2.0 qualification

The committed evidence is `benchmarks/results/BENCHMARK_LIVE_EXTENSIVE_V122.json` plus the human-readable companion report. `v122` is an engineering evidence identifier, not the package version.

The broad matrix contains 30 workload/size/traffic configurations. Each configuration compares real transformed `portable`, `fast+ctypes`, and `fast+native` implementations, validates results before timing, and aggregates fresh-process measurements. The broad matrix accounts for **202,798,080 timed dispatches**, excluding warmups and correctness checks.

Selected measurements on the certified CPython 3.13.5 Linux x86-64 host:

| Workload | Routes / pattern | Portable | ctypes live | native live | Native vs portable |
|---|---|---:|---:|---:|---:|
| VM dense | 64 / random | 250.4 ns | 209.6 ns | **147.4 ns** | **1.70×** |
| VM dense | 256 / skewed | 258.4 | 191.8 | **145.0** | **1.78×** |
| VM dense | 1,024 / random | 361.2 | 245.4 | **193.0** | **1.87×** |
| VM dense | 1,024 / skewed | 330.6 | 212.9 | **160.5** | **2.06×** |
| VM dense | 2,048 / random | 393.3 | 212.6 | **159.2** | **2.47×** |
| Parser integer | 256 / skewed | 289.0 | 203.2 | **156.5** | **1.85×** |
| State machine | 128 / random | 152.9 | 169.9 | **121.1** | **1.26×** |
| HTTP string | 64 / random | 230.7 | 247.5 | 230.0 | ~1.00× |
| Sparse protocol | 256 / random | **237.1** | 295.7 | 242.2 | 0.98× |
| Heavy server | 256 / random | **406.3** | 443.3 | 427.6 | 0.95× |
| Direct/minimal | 256 / random | **49.7** | 83.2 | 62.2 | 0.80× |

Long-loop confirmation matters more than a tiny microbenchmark for this architecture. A 1,024-route skewed VM sample with **10,000,384 dispatches per timing sample** recorded approximately:

```text
portable       329.4 ns/dispatch
ctypes live    222.5 ns/dispatch
native live    169.0 ns/dispatch
```

The equivalent 10-million-dispatch HTTP string-routing workload remained essentially tied:

```text
portable       228.9 ns/dispatch
native live    231.2 ns/dispatch
```

This is the intended interpretation: live is a structural optimization for repeated heterogeneous in-frame routing, not a blanket faster-switch claim.

## 9. Server and async behavior

A one-router-call-per-request 64-route control measured approximately:

```text
portable                  135.9 ns/request
shared fast native        141.0 ns/request
thread_local native       246.2 ns/request
```

Safe live modes therefore do not make sense for ordinary short HTTP routing merely because a server is “hot”. The outer-call structure matters.

Coroutine functions use isolated/per-call live clones. In the server benchmark, roughly 256 dispatches per coroutine invocation favored portable; around 4,096 was near parity; only very large per-coroutine loops began to amortize clone overhead.

## 10. Code size and compilation economics

Portable statement-template lowering can dramatically shrink repeated source shapes. In the qualification evidence, a 256-route HTTP router compiled to only hundreds of bytes in the portable form while the live representation retained tens of kilobytes of inline route bodies. This is a primary reason live should not override a strong portable template simply because route count is large.

For dense VM routes, the extra live compile cost amortizes quickly when the function is actually hot. For compact HTTP/template routes, the theoretical break-even can be tens of millions of dispatches and may never materialize in the whole workload.

Future automatic live selection should therefore be **plan-aware**, not route-count-only: a strong direct/expression/statement portable plan should veto automatic live selection, while a large general/balanced dense-int plan is a much stronger native-live candidate.
